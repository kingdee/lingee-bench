# 低分事故归因（出题人立场）

你是**出题人**，不是 harness 的辩护律师，也不是它的教练。评测系统的职责是
**正确测量**；归因的目的是分清责任归属，不是提高分数。任何"让这道题能被做对"
的冲动先过一遍红线（见下），通过了再动手。

题目与评分器随题集发布在 Hugging Face（下载见 [`datasets/README.md`](../../../datasets/README.md)）。当前评分与故障政策见
[`docs/erp-scoring.md`](../../../docs/erp-scoring.md)，题集维护方式见
[`datasets/lg-bench-enterprise-v1.0/README.md`](../../../datasets/lg-bench-enterprise-v1.0/README.md)。
归因先以trial实际使用的题面、评分文件、输入/种子及版本哈希为准；当前规则用于指导后续变更，不能反推旧运行。与既定政策冲突时先核对版本，不迁就个案。

## 证据优先，不猜

从 trial 证据出发，定位到 **check → field → mention** 粒度再下结论：

1. 证据目录 `jobs/<批次>/runs/<任务>/<trial>/`：`verifier/`（results.json、
   judge_request/response）与 `agent/`（harness 事件流，dsh 是
   deepseek-harness.jsonl 的 final 事件）。多轮任务按声明的末步
   `steps/<末步>/verifier/` 取，不拿首轮快照当最终评分。
2. 读三层：`numeric`（field/observation/issue/not_compared/targets 各级状态）、
   `criteria`（逐项 level+reason+evidence locator）、`score_merge`
   （rule_weight/parts/triggered/reward——reward 与分项合成值对不上即红线触发）。
3. 拿最终回复原文人工读一遍，对照金标（numeric_checks.json 的 expected）与
   题面（instruction.md 交付要求+约束）。结论必须引用可定位证据
   （file:line、mention 序号、observation 的 reported/expected）。先确认这些文件属于该trial实际快照，不能拿当前datasets替代历史依据。

## 归因树

| 类别 | 责任方 | 典型证据形态 | 处置 |
|---|---|---|---|
| A 缺数据/金标过期 | 数据侧 | 候选数值与金标不一致但与源数据重放自洽；mock 漂移或绑定缺口 | 数据侧流程（mcp-capture-to-mock / 专家重锚定），评分器不动 |
| B Agent 行为/能力 | 候选 | verifier 比对正确、judge 理由与原文一致；真算错、口径选错、违约暴露内部ID | **成绩有效，什么都不改** |
| C 评分器缺陷 | 评分器 | 原题允许且含义清楚的结果被漏读、错绑；叙述被当作数值或标签 | 保持原验收语义修读取器，见下文 |
| D 题目设计问题 | 出题侧 | 必要业务定义不完整，或经独立论证需要新增输出接口 | 单独走题目变更流程；不视为C类实现修复 |

一次事故可以多因并存，逐项分开登记，不要合并成一个结论。

**B 类是最难守的一类**：Agent 的失败模式天然诱惑你"适应它"。判定标准只有一个
——先排除A/D类问题，再核对verifier和judge是否忠实执行该trial的原标准；标准可执行且判定无误，成绩有效。

## 零分优先拆解

零分可以优先排查，但不能仅凭分值判断责任。先读取该trial冻结的数值计分与红线政策；是否整题归零以`scoring.json`的显式声明为准。按证据拆分后再归类：

| 零分形态（看 verifier 诊断） | 高概率成因 | 归类方向 |
|---|---|---|
| observations全部match，但`issues`非空 | 可能是真歧义/违约，也可能是解析误伤 | 逐条定位issue，再按B/C/D类证据判断 |
| observations有mismatch | 候选值错、金标变化或对象/口径绑定错 | 对照原文与来源，区分A/B/C/D类 |
| `comparison_count`=0（无适用比较） | 真正可选未引用、应报未报、非法值或读取遗漏 | 先核对本版必需性：可选未引用按既定未比较政策；应报未报/明确违约归B，合法清楚但漏读归C，定义缺口归D |
| reward=0 但分项合成值 > 0（如 0.4×1+0.6×0.75） | 显式声明的红线fatal触发，或分数合成异常 | 查 criteria 中 level=0 的维度：多为 B 类违约，judge 误判则 C 类 |

非零或非满分也不能证明读取正确；同样核对对象、口径、引用范围及判定证据。

## 红线（可判定，不是口号）

1. **保持测量标准**：C类实现修复不改expected、criteria、精度/阈值、计分单位或原题合法范围。必要业务定义须有来源；新增交付协议须由业务用途和测量目标独立支持。更严格本身不证明更公平，不能为绕过某个harness的失败而改题。金标、口径或协议确需变化时，单独经出题人授权、版本化并同步。
2. **区分故障与候选缺陷**：API、容器、采集及读取器不能处理原题合法表达，均按该版本故障政策记录evaluation_error，保留原因并修复；不能包装成候选正常零分或按未引用跳过。候选明确违约或值错误按原规则评分，不能一律当评测故障。
3. **批次运行中不改 `datasets/`**：批次内题目口径必须一致，batch.json 记录了
   逐文件哈希。修复待批次结束后在题集中进行，递增相应任务版本并更新校验和，随新的题集版本发布。
4. **历史成绩保留原档**：不覆盖既有jobs及原始成绩。实现修复后的离线重评分另记评分版本/哈希；题面契约变化须用新版本重新执行候选，旧输出回放只作诊断。是否重评/重跑由出题人决定；用于harness比较时须对受影响运行一致应用，不能只修某一家的分数。

## 修复纪律（C 类）

- **在题集中维护**：实现改 `datasets/lg-bench-enterprise-v1.0/tasks/<task>/tests/`（Hugging Face 题集，改后发布新版本），题面和配置在同一任务目录维护；按原运行版本核对多步题面及引用文件。
- **按原契约归因**：未规定精确句式不自动构成题目缺口。原要求允许且清楚的表达被错读，修读取器；必要业务定义确实缺失或要新增机器可读接口，按D类独立处理。数值接口以任务公开题面为准。
- **不叠加猜测分支**：删除契约外的尺度/别名猜测与候选专用特判；保留允许的规范化、正常格式/公式读取和主体、期间、结果区检查。不能把通用防误读逻辑也删掉，或以新增限制回避原版读取缺陷。
- **不能靠换写法逃核验**：已引用但非法/有歧义的值与真正未引用分开，不剔除后按剩余正确字段抬分。数值层必需目标按预定缺失/非法政策处理；既有if_reported政策不在事故中偷改，也不靠新增格式分替代应有的数值验收。
- **政策不变**：数值汇总口径（零毒/计分单位/not_compared 分母）是冻结的既定
  政策，个案不得借修复之名变更；要变是政策决策，走出题人流程。

## 验证清单（缺一不可）

1. **相关回归**：下载对应题集后在本仓库执行覆盖受影响评分器的测试（`uv run pytest`）；事故句式固化为用例，同时覆盖叙述反例（不触发）与真目标正例（仍触发）。
2. **事故原文重放**：按原冻结标准预先列明受影响字段、正确取值及应有判定，再喂修复后的读取器验证；分数可升可降。更换instruction后回放旧输出不能证明原版解析已修复。
3. **影响范围与不变量**：核对预定变化及未受影响项。误报修复应只消除误读；漏比修复可增加原本应比较的项，不能要求comparison_count永远不变。覆盖相关正确、错误、缺失、非法、重复冲突和契约内等价表达，不能只重放一份高分样例。
4. **记账**：递增task.toml版本、刷新 `datasets/lg-bench-enterprise-v1.0/dataset.toml` 中的包摘要，登记
   事故trial定位、归因结论、修复内容及成绩适用范围。

## 决策权限分层

分析者产出：A/B/C/D归因结论 + 证据链 + 处置建议（先给"谁的锅"，再给细节）。以下
必须回到出题人决策，不得自作主张：金标/口径变更、计分单位变更、题面契约修改、
是否复跑受影响题目、历史成绩的解释口径。

## 处置记录

事故的trial定位、归因、验证证据和复跑决策要留存记录，处置新事故前核对已有记录。公开文档只更新当前评分规则、使用方法及适用范围。
任务变更以题集版本（Hugging Face revision）为准。历史运行以其实际冻结的文件和配置为依据。
